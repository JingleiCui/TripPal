# travel_agent：面试讲解与学习任务

## 90 秒介绍

这个项目是面向国内自由行的旅行规划与行程协同助手。目标不是生成一篇攻略，而是把用户的日期、预算和偏好转换成带地图、来源和可修改版本的行程，并在变化后保留已经确定的安排。

我使用 FastAPI 构建后端，LangGraph 管理需求确认、调查、编排和校验，LangChain 封装工具调用；MySQL 保存业务数据和检查点，Redis／Celery 承接异步任务，Elasticsearch 检索用户导入的资料。前端是 React 工作台，把日程、地图和执行过程放在一起。

主要设计有三点。第一，把开放式调查交给 Agent，把日期、费用、权限和版本交给代码，避免模型越权或凭空补数据。第二，修改基于明确版本，并保留锁定条件；后台使用任务回执和租约，解决重复消息与故障恢复。第三，保存来源和信息缺口，未知费用不算零元，路线未核实不展示成已经确认。

目前已经完成本地数据库和浏览器工程验收，以及本地模型在合成快照上的三策略冒烟。高德、美团和云端模型的完整联调还需要个人开发凭证。因此这是个人项目，不表述成公司生产上线经历，也不使用合成数据推算真实用户提效。

## 展开稿：约 10—15 分钟

### 1. 先说明业务判断（约 1 分钟）

我选择旅行场景，是因为它同时具有开放需求和明确约束。用户可能说想轻松一些、想看历史文化，这部分需要理解和权衡；但景点有没有开放、交通要多久、预算是否足够，不能仅靠语言模型回答。用户还经常修改计划，最怕的是改了一个景点以后，已经确定的安排也被重写。

所以我把产品的核心对象定义为“有版本的行程”，而不是“聊天消息”。每个版本包含出游条件、每天的地点、路线、来源、费用中已经知道的部分以及待确认事项。聊天只是修改这个对象的入口之一。地图、资料和普通页面也可以访问同一个业务对象。

这决定了系统为什么需要数据库、异步任务和前端工作台，而不是仅写一个大 Prompt。我希望用户能看到系统查了什么、依据是什么，出错后还能继续，而不是只能重新问一次。

### 2. 需求拆解和范围控制（约 1 分钟）

第一阶段重点是北京及周边一到三日游，包含城市与正规公园景区。先把一条链路做完整，再扩展城市。输入包含日期、出发位置、天数、人数、预算、交通方式和偏好。日期、出发位置缺失时先追问，因为它们会影响路线、天气和住宿条件；预算可以为空，但不能在缺预算时声称满足预算。

对于轻户外，我没有让模型凭普通步行路线生成野山线路。地图能查到一条线，不等于那条线适合进入，更不等于具备天气和安全保障。当前只做有明确来源的正规公园景区候选，进入条件和景区内部步行仍需核实。这个边界是产品判断的一部分。

预订也分清楚：返回外部链接属于信息服务；用户在平台下单成功属于另外的交易系统。项目没有接订单回调，因此不会把点击链接写成“已经订好”。

### 3. 架构和职责分配（约 1.5 分钟）

我采用模块化后端，没有一开始拆很多微服务。FastAPI 负责账户、权限、行程、资料和任务接口。MySQL 是业务状态的权威。Redis 用于缓存和消息，Celery worker 处理较长的调查任务。Elasticsearch 保存派生索引，原文仍保存在文件目录并由 MySQL 记录归属与版本。

Agent 层用 LangGraph 明确组织节点：需求确认、安排调查、目的地调查、其他领域调查、编排行程、代码校验和必要取舍。LangChain 用来定义类型约束工具和接入模型。主 Agent 根据任务选择领域，目的地 Agent 查地点，交通领域核查天气等信息，住宿领域查询商品。实际路线在候选安排确定后由工具查询。

这里有一个重要取舍：多 Agent 用于工具权限和上下文隔离，不是为了增加模型数量。目前领域执行是顺序的。简单问题应保留直接查询路径；在合成快照的一次本地模型冒烟中，多 Agent 比单 Agent 更慢，所以不能预先宣称它提升了效率。

### 4. 走一遍首次规划请求（约 1.5 分钟）

以北京三日公共交通游为例。前端先提交结构化条件和自然语言目标，API 从登录会话确定用户，生成任务回执。接口很快返回任务 ID，浏览器通过 SSE 看执行过程，而不是一直等待一个长 HTTP 请求。

Worker 领取任务租约，图流程检查条件。信息完整后开始调查。模型可以提出搜索关键词，但只能调用为它注册的工具；地点工具固定查询本次目的地城市，不允许模型任意指定用户、数据库或者网络地址。平台结果归一化后保存来源和获取时间。

编排时，模型只能从实际候选地点 ID 中选择。接着代码检查是否出现重复地点、排除地点或遗漏锁定项目。地点顺序确定以后，查询实际路段，汇总时间、缓冲和已知费用。开放时间和预约条件没有依据时保留未知。最后，确认任务租约和行程基准版本都仍有效，才在事务里写入新版本和完成回执。

地图和日程使用同一份计划，避免页面画了一条线、文本却写另一条路线。高德坐标保持 GCJ-02，不和外部 WGS-84 数据直接混用。

### 5. 讲最重要的可靠性挑战（约 2 分钟）

第一个挑战是重复执行。Celery 不是“恰好一次”系统，消息可能再次投递。我没有把防重全部放在 Redis，而是在 MySQL 保存幂等键、请求摘要和任务状态。同一个键提交不同参数会冲突。Worker 重放已经完成的任务时直接退出。行程提交还检查版本，因此即使两个修改任务都开始调查，也只有符合基准版本的结果能够写入。

第二个挑战是旧 worker。仅仅在 Redis 加锁不能说明失去锁的进程会停止。我给任务设置租约、心跳和执行 token，调用工具之前、模型返回后和最终事务前都检查。租约到期被新 worker 接管后，旧 token 不能继续提交。读取平台的操作可能重复，这是可接受且要记录的成本；重复生成业务版本不可接受。

第三个挑战是修改破坏既定安排。我的实现保留锁定地点，并检查日期和已锁定时间。改变日期、路线衔接不过来时不静默调整，而是明确要求修改条件或解除锁定。恢复历史版本也不是删除后续历史，而是创建一个新的版本。

第四个挑战是错误兜底。如果下游超时，只读查询可以有上限地退避重试；参数不符合 schema 可以给模型一次纠正机会。但不能为了“看起来成功”返回一个猜测的价格或路程。工具结果错误、模型结构错误和配置缺失要分别记录，用户可以看到哪一步缺信息。

### 6. 上下文、资料和来源（约 1.5 分钟）

上下文管理不是把所有消息一直追加。我保存结构化目标、约束、确认偏好、待办以及旧版本地点，近期调查结果按职责提供。用户主动保存的偏好与从模型推断的东西分开。Graph 检查点用于当前任务恢复，MySQL 用户偏好用于跨任务复用，两者不是一个概念。

私人资料支持文字、PDF、DOCX 等解析。切分保留页码、段落和表格位置，使用 450 字符窗口、80 字符重叠；这是字符而非 token。Embedding 使用 BGE 中文小模型，归一化后的 512 维向量。ES 全文检索和向量检索各取候选，使用 RRF 融合。是否启用重排需要单独评测，不能因为技术栈好看就默认增加耗时。

权限过滤在召回时执行，不能先把其他用户的内容搜出来再交给模型筛。版本更新先索引后发布，失败保留旧版；删除先取消可见性。检索得到相关片段也不代表回答一定正确，仍要检查适用条件和来源。目前不宣称已经理解文档里的图片或复杂图表。

### 7. 评测和性能怎么讲（约 1 分钟）

我把工程回归和模型质量分开。六十条合成案例覆盖城市、景区、锁定、室内、缺失信息和版本冲突，分成开发、验证和保留家族。回归运行真实图流程和数据库，但采用固定平台夹具，不调用模型；它检验的是状态和业务约束，不能作为模型效果。

真实模型另外跑纯模型、单 Agent 和按需多 Agent，保存模型名称、输入集哈希、原始结果、调用次数和延迟。当前只有本地模型冒烟，没有足够样本证明质量提升。我也没有把纯模型文本因为缺少结构化字段就直接判业务失败，语义和引用支持需要逐例评阅。费用要在真实 Token、地域和价格确认后计算，没返回用量就记未知。

### 8. 当前边界和下一步（约 1 分钟）

项目已经完成本地工程链路，前后端、数据库、队列和检索可以实际运行。但真实地图和酒旅平台需要账号凭证，真实价格和开放信息具有时效性。语音接口作为可选接入保留，未完成真实账号验证前不写成已经部署验证。

下一步我优先处理真实案例中的失败：比如候选地点召回不足、开放信息缺失、改计划导致时间冲突，然后在相同数据与模型下比较修复前后。如果简单路径已经足够，就减少 Agent 和调用；如果跨领域上下文确实造成错误，再增加隔离。我的核心价值是判断哪些事实必须查询、哪些约束必须由代码强制，以及如何证明完成，而不是列出更多框架名字。

## 三层追问与回答抓手

| 面试官问 | 第一层回答 | 再往下准备 |
|---|---|---|
| 为什么不用直接聊天？ | 持久行程、版本修改、实际工具和可追踪执行 | 锁定、冲突、恢复的具体代码 |
| 为什么多 Agent？ | 按领域隔离上下文和工具，按需使用 | 顺序执行、开销、单 Agent 对照失败例 |
| 工具调用不稳定怎么办？ | schema、错误类型、有限纠正、只读退避 | 429／超时／错误结构的测试 |
| Redis 挂了怎么办？ | SQL queued 回执仍存在；恢复后派发 | 不能声称业务写入全部不可重复 |
| worker 死了怎么办？ | 租约过期接管、检查点与 token | 节点重放、只读重复成本、最终提交门禁 |
| 日期改了锁定项目怎么办？ | 冲突需要明确取舍，不静默移走 | 锁定日期和开始时间校验 |
| RAG 数据更新怎么避免空窗？ | 新索引完成后切换可见版本 | 失败旧版、权限过滤与删除回查 |
| 如何保证回答真实？ | 来源约束和未知信息显式展示 | 不能保证所有语义正确；需要评阅 |
| 二十轮记忆有没有测？ | 目前未完成足够真实模型长对话验证 | 结构摘要只能减少风险，不能当作证明 |
| 有没有生产效果？ | 这是个人项目、本机验证 | 不把合成状态匹配写成生产成功率 |

## 逐步学习任务

每次只做一项，完成后再进入下一项：

1. 运行合成一日游，找到 task、trip、revision 三条关系，解释为何任务和行程分开。
2. 锁定一个地点，修改行程，查看版本和差异；复写“禁止遗漏锁定项”的校验。
3. 提交缺少日期的任务，重启后继续，说明 interrupt 与普通函数返回的区别。
4. 看一次 Trace，区分模型耗时、工具耗时和队列等待；解释为何不能只测总请求时间。
5. 上传自己的文字攻略，追踪原文、片段、向量和召回结果；手算两个列表的 RRF。
6. 阅读 acquire 与最终提交，复写旧 token 拒绝逻辑。
7. 配置真实平台后一条一条验证，记录一个实际失败；用“问题—判断—实现—证据—边界”复述。
8. 最后脱离文稿，90 秒讲清业务，5 分钟讲透一项挑战，再接受三层追问。
